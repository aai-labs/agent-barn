# Honcho backs Agent memory, scoped to one workspace per Agent

Status: Accepted
Date: 2026-09-03
Origin: [AF-280](https://aai-labs.atlassian.net/browse/AF-280)

Agent memory is currently Markdown on the Agent's PersistentVolumeClaim plus OpenClaw's file-backed `memory-core` slot with embedding search disabled, so what an Agent has learned is readable only from inside its own pod and nothing on the platform can query it. Honcho becomes the memory backend for opted-in Agents, with one Honcho workspace per Agent. How it sits differs by runtime, because the runtimes differ: in OpenClaw it occupies the single memory slot instead of `memory-core`, while Hermes takes it as a memory provider alongside `MEMORY.md` and `USER.md`, which stay the operator-editable baseline. The goal is memory quality and platform-readable memory. Isolation stays per-Agent by default; selective cross-Agent sharing is layered on top as an explicit, operator-driven promotion (see **Consequences**) rather than any form of automatic or workspace-level merging.

## Considered alternatives

- **Enable embedding-backed search on the existing `memory-core` slot** — rejected as insufficient alone. It is materially cheaper and adds no service, but memory stays pod-local, so no platform surface can show an owner what their Agent learned.
- **Adopt `@openclaw/memory-lancedb` as the memory slot** — rejected for the same reason. It keeps per-Agent vector memory on the existing PVC and routes embeddings through LiteLLM on the Agent's own key, but remains pod-local and models no individual participant in a shared room.
- **One shared Honcho workspace per Organization** — rejected. It crosses the Agent Access boundary: conclusions derived from one Agent's conversations would reach a user who has access only to another Agent. The procedural half of shared learning — reusing packaged instructions across Agents — is already delivered by Organization-scoped Skills.
- **Run Honcho beside `memory-core` rather than replacing it** — rejected. The runtime exposes a single memory slot, and two independent writers over the same semantic state is the condition this decision exists to remove.
- **Attribute memory spend from the request path** — not possible, and not needed. Honcho `v3.1.0` resolves model credentials per module rather than per workspace and sends no workspace identifier, so LiteLLM sees one undifferentiated stream. Attribution comes from Honcho's per-call telemetry instead.
- **Apportion the shared credential's spend by message volume** — rejected. An estimate rendered beside measured figures is read as measurement; token counts make the split measured, so no estimate is required.
- **Purge the workspace inline in `delete_agent`** — rejected once the upstream contract was read. It matches how the PersistentVolumeClaim and other Kubernetes resources are already deleted, but a single workspace delete returns 409 whenever a session is active, which is the normal state for an Agent that did any work. Best-effort inline deletion would therefore have failed silently in the common case rather than the rare one.
- **Purge the workspace as a retried Domain Event delivery on `agent.deleted`** — implemented, reversed in favour of retention, then adopted after all. The reversal reasoned that destroying memory was inconsistent with the Agent's row and audit history surviving, and that it foreclosed reusing a deleted Agent's memory. Both points were answered rather than dismissed: the surviving row is audit metadata rather than content, and carry-over gives that memory an explicit destination at deletion time, which is the reuse the reversal was protecting. The 409-on-active-session problem this option was designed for is real — confirmed against a live workspace — which is why the purge is a retried delivery and not inline.
- **Migrate existing Markdown memory into Honcho automatically on enable** — rejected. Uploading seeded and Agent-written files produces representations that compete with what the deriver subsequently infers, and unpicking that is harder than a cold start.

## Consequences

- A workspace is named from the Agent identifier, so workspace ownership is derivable rather than tracked in a mapping table.
- Selective cross-Agent sharing is an explicit promotion, not automatic. An operator supplies specific content and a set of destination Agents; it is written into each destination's Honcho workspace, authorized per destination through the existing `AgentAuthorization` (`AGENT_READ` on the source for audit context, `AGENT_MEMORY_MANAGE` on each destination — writing into an Agent's memory is the same power as editing it directly). Nothing is read out of a source Agent's memory — the operator's own knowledge supplies the content — so this needs no read path into Honcho and does not touch per-Agent workspace isolation. Org-scoped shared workspaces (full peer-level merging) remain rejected for the RBAC reason recorded above.
- Copying is the only mechanism available, not a shortcut past a better one: Honcho has no cross-workspace sharing and is not going to grow one, because `workspace_name` participates in nearly every composite foreign key — isolation is structural rather than policy — and `clone-session` operates within a single workspace.
- A shared fact is written as a **conclusion on the destination's own self-model**, both sides of the `(observer, observed)` pair being its AI peer, using the peer name each runtime builder already sets (Hermes) or that Honcho's own OpenClaw integration fixes (`agent-main`). This replaced an earlier design that posted a message from a synthetic `shared-memory` peer: Honcho stored those messages and reasoned over them correctly, but the runtime's own recall never looked there, so sharing returned success while doing nothing observable. Live testing showed conclusions are recalled and side-session messages are not. Both conclusion placements (self-model and user peer) recall equally well, so self-model is chosen on semantic grounds — shared knowledge is something the Agent knows, not something it observed about a person — and because it needs no guess at a user peer name, which differs per runtime and per sender.
- Provenance is tracked in `shared_memory_fact` on our side, because Honcho's `ConclusionCreate` accepts no metadata. Without it a shared fact is indistinguishable from a self-derived one — it sits in exactly the same place — and the memory view would present a fact an Agent was handed as one it reasoned its way to. The row follows a correction to the replacement conclusion's id, and survives deletion of either Agent (`SET NULL` on the source) so a memory can still say it was shared even when the sharer is gone.
- Memory spend is attributed per Agent, and therefore per Organization, from Honcho's own telemetry rather than from LiteLLM's view of the request. Honcho emits a per-call event naming the workspace and counting tokens; those shares divide LiteLLM's authoritative spend on Honcho's single credential, so per-Agent figures are measured and always reconcile to the real total. The sampling rate for those events is pinned to 1.0: below it they are sampled, and every share silently undercounts.
- Honcho holds a dedicated LiteLLM credential, never the master key. The master key can mint and revoke every other key, and its spend is not a per-key line any report reads, so using it would forfeit both least privilege and the total the token shares divide.
- Honcho's `dream` subsystem is enabled by default and performs background model work on an idle timer, so memory accrues cost with no user action at all. That cost is attributed like any other, but it accrues whether or not anyone used the Agent, which is why it is disabled by default.
- Deleting an Agent erases its Honcho workspace. Deletion already destroys the PersistentVolumeClaim, the Secret, the Deployment and every other resource, and there is no restore path anywhere in the product — the soft-deleted row exists for audit and cost history, not for bringing an Agent back. Retaining derived conclusions about real people, owned by an Agent nobody owns and under no retention policy, would have been the odd exception rather than a safeguard. This reverses the retention decision recorded earlier in this ADR; what changed is that explicit carry-over now exists, so the knowledge an Agent accumulated has somewhere to go.
- The purge runs as a retried delivery on `agent.deleted`, not inline in `delete_agent`. Honcho refuses a workspace delete with 409 while any session remains — the normal state for an Agent that did any work, verified against a live workspace — and both the session and workspace deletes are accepted asynchronously, so deleting sessions first still races. Inline, a lost race would leave the memory in place behind a log line, and there is no longer any view in the product that could reach it. Under the delivery framework the failure is retried until the purge takes.
- Carry-over is offered in the delete flow rather than left to ordinary sharing. Sharing one fact at a time requires knowing in advance which facts matter, at the moment people have least foresight: deletion is usually "this Agent is redundant", and the loss is noticed later. The delete dialog copies the whole workspace into chosen Agents first and aborts the deletion if that copy fails, bounded at 500 memories with the truncation reported before anything is destroyed.
- No retention question remains for memory: it does not outlive the Agent. This deliberately differs from `2026-07-31-retain-security-audit-records-across-product-deletion.md`, which retains audit records across deletion — audit records are a record of what was done, whereas memory is conversational content about real people, and keeping the latter indefinitely needed a justification that carry-over removed the need for.
- Memory is opt-in and defaults to off. A running Agent keeps `memory-core` until it is stopped and started once, because runtime configuration is built during start and never rewritten in place.
- Disabling Honcho is asymmetric. Markdown memory is never migrated away, so it is intact on return, but anything learned while Honcho was active is not written back to Markdown and does not survive the switch.
- Hermes resolves its provider config from `$HERMES_HOME`, so that variable has to be set to the mounted state directory. Left unset it looks under the home directory instead, and the configuration is silently never found.
- The runtime's Honcho peer mapping must be stored on the Agent's PVC. Held anywhere else it is lost on pod recreation, and each participant silently becomes a new peer.
- Honcho requires a pgvector-capable PostgreSQL of its own and a Redis database index distinct from Firecrawl's.

## Revisit when

Revisit if platform-readable memory does not in practice produce the owner-facing visibility it is being adopted for; if pod-local memory gains an equivalent platform read path, which would remove the main reason `memory-core` and `memory-lancedb` were set aside; if Honcho stops emitting per-call workspace telemetry or makes those events sampled by default, either of which removes the basis for attributing memory spend; or if embeddings should move to a self-hosted model, which routes through LiteLLM like any other and needs no code change, but is only cheap before real memory exists — Honcho enforces the embedding dimension as immutable for a deployment's life and cannot detect a same-dimension model swap, so changing either afterwards means standing up a second deployment and replaying data rather than editing configuration. Also revisit if a read path into Honcho memory is ever built (for AF-184-style observability): at that point promotion could pull directly from a source Agent's actual stored memory instead of depending on the operator's own knowledge, which is a materially different and stronger feature than what exists today.
