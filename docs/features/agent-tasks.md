# Agent Tasks

## Read when

Read before changing Tasks, Task Notes, Task Files, how Task Files use Artifacts, or who can read them.

## Role in the system

A Task is a piece of work an Agent records for itself, with a timeline of Task Notes and the Task Files it produces. Tasks live in Agent Barn's own tables in the application Postgres, not in a separate tracker, and their files are [Artifacts](agent-artifacts.md); [`../adr/2026-10-21-native-agent-task-store.md`](../adr/2026-10-21-native-agent-task-store.md) records why.

The store and its service live in `../../api/domains/agent_tasks/`. Agents write and read their own Tasks through the routes and command below; people read them in the dashboard (see How people read Tasks).

## Invariants

- A Task belongs to one Agent and carries the same Organization identity. The database enforces this with a composite foreign key to the Agent.
- A Task has a title, an optional description, and a status of `open`, `in_progress`, `done` or `failed`. It starts `open` unless the Agent creates it with another status, and its Agent may move it to any status.
- A Task's origin is `agent` when the Agent recorded it and `automatic` when its runtime's Task plugin did, because the Agent did work without recording it. It is a label for readers, not a permission: both come through the Agent's own key.
- Task Notes are append-only and listed oldest first. Adding a Note, or attaching or removing a File, counts as a change to the Task, so it moves up the most recently changed lists.
- Only the Task's own Agent writes: it creates Tasks, changes their status, adds Notes and attaches Files. The write methods take the Agent's Organization and id, which the caller has already authenticated, and refuse a deleted Agent or another Agent's Task with 404. People have no write path.
- People read Tasks with `task.read`, which every locked Agent Access Role grants. Reads filter by Agent visibility in the query: one Agent's Tasks, one Task with its Notes and File metadata, a download link for one File, or every Task across the Organization the reader can see. The Organization list keeps only Agents the reader has both `agent.read` and `task.read` on, as the per-Agent reads do. Lists put the most recently changed Task first and can be filtered by Agent and status; an Agent the reader cannot see simply yields no Tasks. An Agent the reader cannot see returns 404; one they can see without `task.read` returns 403. See [`rbac/IMPLEMENTATION-BRIEF.md`](rbac/IMPLEMENTATION-BRIEF.md).

## How an Agent records Tasks

- Every Agent, on both Hermes and OpenClaw, runs the `agentbarn-tasks` plugin (`../../api/domains/agents/scripts/hermes/plugins/agentbarn-tasks/`, `../../api/domains/agents/scripts/openclaw/plugins/agentbarn-tasks/`), enabled for every Agent. Keeping Tasks does not rest on the prompt alone:
  - It registers an `agentbarn_task` tool with typed actions (`create`, `status`, `note`, `attach`, `remove_file`, `list`, `show`). The tool runs `agentbarn-task` underneath, so the command stays the one client of the routes. `create` starts a Task `in_progress` unless told otherwise, and `create` and `status` take a `body` that becomes a Note in the same call, so recording a job takes one model call rather than three or four.
  - Each turn starts with the Agent's open and in-progress Tasks and its three most recently finished ones, so a stale `in_progress` Task stays in front of the model and a follow-up can reopen the Task it continues rather than start a duplicate. Hermes adds them in `pre_llm_call`, OpenClaw in `before_prompt_build`. They come from one listing of the Agent's latest 100 Tasks, most recently changed first, with a 10-second limit; the result is cached for a minute and refreshed after any Task change. A listing that fails or runs out of time is cached the same way, as no Tasks, so a slow Task service costs one turn at most ten seconds rather than holding up every turn. The list is the Agent's, not the session's: every conversation the Agent has sees the same Tasks, including automatic titles taken from another person's request. The Agent is the boundary, as it is for its files and memory; people who should not see each other's requests need separate Agents.
  - It watches each turn. Only a Task call that changed a Task (`create`, `status`, `note`, `attach` or `remove_file`, or the same command run from the shell, by name or full path, not merely mentioned in it) and did not fail counts as recording the turn's work: a tool answer with an error, or a command that exited non-zero, does not count. Hermes reports a failed command only through its `exit_code`, and OpenClaw only through `details.exitCode`, so the plugins read those; listing or reading Tasks does not. A turn counts as real work when it makes three or more tool calls, or writes any file (Hermes `write_file`/`patch`, OpenClaw `write`/`edit`/`apply_patch`), whatever its length. A write that failed produced nothing and does not count. A patch written as a patch body names its files only in the body, so the plugins take the files the runtime reports back (Hermes `files_created`/`files_modified`, OpenClaw `details.summary`). Real work without a Task gets a reminder in the tool result the model reads next (Hermes `transform_tool_result`, OpenClaw `tool_result_persist`). Hermes also holds a turn that wrote files back once before it finishes (`pre_verify`, which Hermes fires only after file edits). OpenClaw's `before_agent_finalize` asks for a revise too, but OpenClaw refuses a revise once a run has side effects, so it only helps runs that changed nothing. If the turn still ends without a Task, the plugin records one when the turn completes: titled with the user's request (shortened to 120 characters, the request up to 2,000 characters as the description), status `done`, origin `automatic`, with the turn's files attached. Credentials in the request are replaced with `[redacted]` first, since people across the Organization can read the Task: common token formats (GitHub, Slack, GitLab, AWS, Google, `sk-` keys, JWTs), bearer tokens, private key blocks, passwords in URLs, values after words such as `password` or `token`, including inside longer names (`DB_PASSWORD=`, `GITHUB_TOKEN=`) and quoted JSON keys, and long words that read like keys (mixed case with digits, or long hex). A next-turn catch-up reminder did this before; in experiment runs the model often ignored it, or caught up with an empty duplicate Task. Hermes runs with a parent session (its background review, which runs in the same session right after a turn, and subagents) get no context and are not tracked, so they never create or trigger Tasks. On OpenClaw, the startup checklist (`BOOT.md`, run in the session `agent:<id>:boot`) and subagent runs (sessions with `subagent:` in their key) are left alone in the same way. Heartbeat runs and the Hermes startup checklist (the `agentbarn-boot` session) are not counted either. The plugin keeps what it tracks (each session's latest request, pending reminders, turns in flight) for at most 500 sessions, forgetting the oldest first, so a long-lived pod with many conversations does not grow without limit.
  - Files a turn writes are attached to the Task it worked on when the turn ends, without a model call: when the turn touched exactly one Task, each written file still on disk and within the size limit is attached through `agentbarn-task attach --replace`, unless the Agent attached it already. `--replace` removes the Task's earlier files of the same name once the new one is in, so a file reworked over several turns is held once; two files of the same name the turn wrote in different folders are both attached, without `--replace`. A file the turn published with `agentbarn-artifacts upload` (from the shell, without `--attempt-id`) is attached the same way, since the Agent published it for the user: that catches a result written by running code or a shell command, which the plugins cannot otherwise see. The instructions tell the Agent which files are attached for it and to attach any other file that is part of the result itself. Files that hold credentials (`.env*`, `.netrc`, `.npmrc`, `.pgpass`, `id_rsa` and other SSH keys, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*credentials*.json`, `service-account*.json`) are never attached automatically, since anyone with `task.read` could download them; the Agent can still attach one on purpose. The Agent removes any that are not part of the result (`remove_file`). A file that could not be attached, one over `ARTIFACT_MAX_BYTES`, or a turn that touched several Tasks, is named in the next turn's reminder instead.
  - When a turn completes, each Task the Agent left `in_progress` in it is marked `done`, also without a model call. A status the Agent chose itself in that turn (`failed`, or `open` while it waits on the user) is kept, and a Task the turn only added a Note to is left alone. A turn that did not complete (Hermes `completed` false, OpenClaw `success` false) gets its files attached, and a Task it left `in_progress` goes back to `open`, so it does not stay in progress indefinitely; nothing is recorded automatically for it. Work that continues in a later turn sets the Task back to `in_progress`.
  - Hermes runs with tool search off (`tools.tool_search.enabled: "off"`). With it on, Hermes hides plugin tools behind a search bridge, and in an end-to-end run the model ignored both the instructions and the in-turn reminder until the tool was loaded. Our Agents have no other plugin or MCP tools, so this adds one schema per request; revisit if MCP servers are added.
  - Every user or scheduled request carries one line (about 40 tokens): create a Task before starting work that needs tools or produces files, or continue an open one, and don't mention it in the reply. Small talk does not: a message of at most eight words, all from a fixed list of greeting and thanks words. Approvals such as "ok" or "yes" are not on the list, since they can start work. In end-to-end runs OpenClaw's model had the tool and the instructions but did not use them within the turn, and OpenClaw refuses a revise once a run has side effects (hard-coded, not configurable); Hermes recorded within the turn without the line, but only part-way through or after the work. The `create` action takes a starting status, which the create request carries, so a Task starts `in_progress` in one request.
  - The instructions and the request line ask the Agent not to mention Tasks unless the user asks; the instructions also cover a user asking where the Agent's work or files are. It occasionally still does (OpenClaw once answered "Ok" with a line about creating Tasks); that is tolerated.
  - On OpenClaw the manifest declares the tool under `contracts.tools`, and the plugin's entry sets `hooks.allowConversationAccess`; without it OpenClaw drops the turn hooks with only a warning.
- Every Agent also has `/usr/local/bin/agentbarn-task` (`../../api/domains/agents/scripts/agentbarn_task.py`, mounted from the Agent's ConfigMap by `../../api/domains/agents/builders/tasks.py`). `AGENTS.md` carries `TASK_TOOL_INSTRUCTIONS`: keep a Task for work that uses tools or produces files, continue an open one where it covers the request, and set `failed` or `open` itself; closing the Task and attaching its files are left to the plugin. The command takes `--note` on `create` and `status`, and `--replace` on `attach`. Unlike Agent Memory, there is no per-Agent switch.
- The command calls the Agent's Task routes on the ingest app (`../../api/domains/agent_tasks/agent_routes.py`, mounted by `../../api/ingest_app.py`) with the pod's `AGENT_ID`, `INGEST_URL` and `INGEST_API_KEY`. The ingest app is where Agents authenticate with their ingest key; the main API authenticates people. The routes belong to this domain and only borrow the key check (`authenticated_agent` in `../../api/domains/ingest/service.py`).
- A Bot (see [Agent Bots](agent-bots.md)) records Tasks as itself, although it runs in its Parent Agent's pod. On Hermes, each Bot profile gets its own copy of the plugin, which runs the command with the Bot's identity from the profile's `.env` (its `AGENT_ID`, ingest key and Artifact credentials) rather than the pod's process environment, all replaced together. A Bot's terminal also passes its own `AGENT_ID`, `INGEST_URL` and `INGEST_API_KEY` through, so `agentbarn-task` run from there acts as the Bot too.
- Routes under `/ingest/v1/agents/{agent_id}/tasks`: `POST` creates (optionally with a starting `status`), `GET` lists (most recently changed first, filter by `status`, up to 100 a page), `GET /{task_id}` shows one Task with its Notes and File metadata, `PATCH /{task_id}` sets the status, `POST /{task_id}/notes` adds a Note, `POST /{task_id}/files` attaches a published Artifact by `artifact_id`, and `DELETE /{task_id}/files/{file_id}` removes a File and releases its pin, so the Artifact expires a full retention period later unless another Task still has it. The Agent and its Organization always come from the key, never from the request, so an Agent only ever reaches its own Tasks; another Agent's Task is 404.
- `agentbarn-task attach` publishes the file as an Artifact first, through the Artifact runtime routes with the pod's `ARTIFACT_URL` and `ARTIFACT_API_KEY` (the same routes and credential as `agentbarn-artifacts`), then attaches it by id with the ingest key. It applies the Artifact command's rules before sending anything: the file must resolve inside `ARTIFACT_UPLOAD_ROOTS` (the runtime's workspace), so a link out of it is refused; it must be a regular file, opened without following a final link; and it must be within `ARTIFACT_MAX_BYTES`. Without Artifact credentials it says files cannot be attached, and the Agent records the work without them. As `agentbarn-artifacts` does, it sends no bytes when storage answers that it already holds them (`READY`), and retries for up to 30 seconds while another publish of the same file holds it (409). With `--replace`, earlier files of the same name are removed only once the new one is attached, and never the File just attached: attaching unchanged bytes returns the File already on the Task. The plugins skip a written file past `ARTIFACT_MAX_BYTES` rather than try it.
- The command passes a 400 or 422 explanation through to the Agent and maps 401 and 404 to fixed messages; anything else is reported as unconfirmed, never as success. A refused publish gets its own messages (401 credential refused, 413 over the file limit, 503 storage not available yet); the storage service's wording is not passed on.

## How people read Tasks

- The user routes are in `../../api/domains/agent_tasks/routes.py`, mounted by `../../api/api_app.py`, in two routers like Playbooks: `GET /organizations/{organization_id}/agents/{agent_id}/tasks` (filter by `status`, `updated_since` and `updated_before`), `GET …/tasks/{task_id}` (with Notes and File metadata), `GET …/tasks/{task_id}/files/{file_id}/download-link` (a short-lived link to the File's Artifact, from `file_link`), and `GET /organizations/{organization_id}/tasks` (filter by `agent_id`, `status`, `updated_since` and `updated_before`, which keep Tasks last changed within those bounds, both inclusive). They are read only; people cannot create, cancel or close Tasks.
- A download follows that link, as the Artifacts tab does: the Artifacts download route serves the bytes from the Agent's Artifact bucket, as an attachment under the File's name. The Task routes never touch the bytes.
- The UI is in `../../ui/src/features/tasks/`: a Tasks tab on the Agent page, shown with `task.read`, and an Organization Tasks page at `/dashboard/[orgId]/tasks` with a rail entry for every member, filterable by Agent (only Agents with `task.read`) and status. The page lists Agents with `include_bots=true`, so a Bot is named and offered as "Bot · Parent Agent", right after its Parent Agent, and its Tasks link to the Bot's own page. Both open on a board with a column per status, each column paged with its own status-filtered list request, and switch to a list (`taskView` on the Agent page, `view` on the Organization page, kept in the URL); the status filter is only offered in the list. Cards and rows show each Task's File and Note counts, and a failed Task's latest Note, from the list routes' `file_count`, `note_count` and `latest_note` (people's lists only; the Agents' own routes are unchanged). A Task opens in a dialog with its description, Files to download and Notes, notes first when it failed; the open Task is kept in the URL (`task=<agentId>.<taskId>`), so it can be linked to and Back closes it. Closing a Task opened on the page steps back over the entry opening it pushed, so Back then leaves the page rather than repeating it. Ids taken from the URL (`task`, `agent`) are used only when they are UUIDs; anything else is ignored rather than sent.
- Boards and lists have the shared date range picker (`../../ui/src/components/date-range-picker.tsx`), as on the activity and costs pages. With no dates picked they show the last 30 days, and the picker reads "Last 30 days"; a picked range is kept in the URL (`taskFrom`/`taskTo` on the Agent page, `from`/`to` on the Organization page) and "Clear dates" returns to the last 30 days. The default counts from midnight, so the lists' cache keys hold for the day. On the board the dates trim only the Done and Failed columns: an open or in-progress Task shows whatever its age, so unfinished work is not hidden. Without the default the Done column would only grow, mostly with Tasks whose files have expired (30 days after the Task finished). Dates with no Tasks say so ("No tasks in the last 30 days.", or "No tasks in these dates."), unless there are none at all.
- Open lists and boards refresh every 30 seconds and when the window regains focus, so a Task an Agent finishes moves column without a reload. Pages are by offset over the last change, so a Task that moved up while pages loaded can come back on a later page; it is shown once. A failed Load more keeps the Tasks already shown and offers a retry beside them; only a first load that failed replaces the list with an error.
- A Task its Agent's runtime recorded (`origin` `automatic`) says "Recorded automatically" on its card or row. A File whose Artifact has expired stays listed; downloading it says it has expired (the 410 from `file_link`). If the Organization's Agents cannot be loaded, the Tasks page says so with a retry, and Tasks still load without their Agents' names.
- Agents point people to the Tasks tab and page when asked where their work or files are (`TASK_TOOL_INSTRUCTIONS`, shared by both runtimes), and still share the result in the conversation, since people on Slack, Teams or Telegram may never open the dashboard.

## Task Files

- A Task File is an Artifact the Agent has published, attached by id. `agent_task_file` holds the Artifact id and copies its name, content type and size; the bytes stay in the Agent's Artifact bucket. Artifacts never change once published, so the copies cannot drift. Name and type were validated when the Artifact was created.
- `attach_file` accepts only a `READY` Artifact of the same Agent and Organization; anything else is 404. Attaching the same Artifact to the same Task again returns the existing File. One Artifact may be attached to several Tasks.
- Each File pins its Artifact (`ArtifactService.pin`, kind `task`, owner the File's id) in the same transaction that records it, so the Artifact does not expire or get deleted by hand while the Task is unfinished. Pinning locks the Artifact row on its first read, so an Artifact a deletion has started on is refused, and two attaches of the same Artifact are serialised.
- A File's Organization is always its Task's: a composite foreign key enforces it.
- `file_link` checks the reader's `task.read` access to the Agent, then returns `ArtifactService.link` for the File's Artifact: a short-lived signed download that the Artifacts download route serves.
- The size limit is the Artifact limit (`ARTIFACT_MAX_BYTES`). There is no per-Organization limit on Task Files; retention and the per-Agent pin limit bound what they keep.
- Without Artifact storage, the Agent cannot publish files, so it can still keep Tasks and Notes but attaches nothing.

### Task File retention

- Files are kept while their Task is `open` or `in_progress`. When the Task moves to `done` or `failed`, the same transaction releases its Files' pins, and each Artifact expires a full Artifact retention later (`ARTIFACT_RETENTION_DAYS`, 30 days by default). A File attached to a Task that is already finished is released at once, so it gets the same retention.
- Reopening a Task does not pin its Files again; they keep the expiry they were given. Files attached after reopening are pinned as usual.
- An Agent keeps at most `MAX_PINNED_FILES_PER_AGENT` (500, in `service.py`) pinned Task Files. Each attach past that releases the Agent's oldest pins, which then expire like any released File. Attaching never fails because of this limit. Concurrent attaches do not serialise on the count, so it can be passed briefly by as many attaches as run at once.
- A File whose Artifact has expired stays on its Task; `file_link` answers 410 ("This file has expired and can no longer be downloaded.") rather than the Artifact's 404, since the File and its Agent were found.

## Deletion

Agent deletion is a soft delete, so the Agent foreign key never cascades. The deletion transaction in `AgentRepository.soft_delete_with_event` calls `stage_agent_task_cleanup` (`../../api/domains/agent_tasks/cleanup.py`), which deletes the Agent's Tasks; their Notes and Files follow by cascade. The pins those Files held are not released: the Artifacts purge removes a deleted Agent's Artifacts whether or not they are pinned. If the deletion rolls back, the Tasks stay. Agent writes hold the Agent row `FOR KEY SHARE`, which conflicts with the deletion's `FOR UPDATE` but not with ordinary Agent updates, so no Task or File can be added after the cleanup ran.
